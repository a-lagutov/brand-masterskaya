# Админка и Telegram-бот

Payload CMS 3 (Next.js) и бот на [grammY](https://grammy.dev) в одном Node-процессе. База — SQLite в одном файле.

## Что в админке

| Раздел                    | Что там                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Заказы**                | Заказы с сайта (обновляются раз в минуту) и добавленные вручную. Правки сохраняются: синхронизация перезаписывает только то, что потом изменилось на сайте. «Создан» задаётся только при создании. У ручных заказов дату оплаты, сумму и позиции чека можно менять после сохранения; финансовые данные заказов с сайта защищены от ручной правки. Очистить «Аккаунт Telegram» — заказ можно привязать заново; «Аккаунт изменён» — когда это было. Удалённые заказы уходят в корзину и не дают доступа в чаты; из корзины их можно только восстановить. |
| **Участники**             | Все, кто писал боту: заказы, «Дополнительно пустить в чаты», «Не пускать в чаты» (бот сразу удаляет из чата).                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Чаты**                  | Появляются сами, когда бота делают администратором чата. Здесь — название кнопки и статус бота.                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Тарифы и факультативы** | Список с сайта (`src/prices.json`). Здесь меняются цены — сайт показывает и берёт их сразу после сохранения (`~/private/<сайт>/prices.json`) — и чаты, которые открывает каждый.                                                                                                                                                                                                                                                                                                                                                                       |
| **Промокоды**             | Код и список скидок: тариф или факультатив и свой процент для каждого; остальное по полной цене. Срок действия, флажок «Действует». Сайт принимает код сразу после сохранения (`~/private/<сайт>/promocodes.json`). У заказа видно, какой промокод применён.                                                                                                                                                                                                                                                                                           |
| **Сценарии**              | Цепочки шагов: сообщение с кнопками, кнопки чатов, состав заказа, пауза. Запуск — командой, кнопкой, по `/start` для новых людей или после подтверждения оплаты.                                                                                                                                                                                                                                                                                                                                                                                       |
| **Тексты бота**           | Встроенные сообщения: приветствие, «оплата подтверждена», ошибки.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

## Как работает бот

- `/start <номер заказа>` — ссылка со страницы «Спасибо» и из письма. Бот читает файл заказа с сайта, проверяет оплату и привязывает заказ к аккаунту: один заказ — один аккаунт. Потом присылает состав заказа и кнопки вступления в чаты, затем сценарии «после подтверждения оплаты».
- Ссылки вступления создают заявки. Бот одобряет заявку, только если чат положен участнику: по тарифам его оплаченных заказов плюс «Дополнительно пустить», минус «Не пускать». Заявки по ссылкам, созданным людьми, не трогает.
- `/start` без номера — снова заказы и чаты; у кого заказов нет — приветствие или сценарии «вместо приветствия».
- Команды из сценариев попадают в меню бота в Telegram.

Бот получает сообщения long polling'ом: хостинг ходит в Telegram, а Telegram до хостинга не достаёт, поэтому вебхука нет.

## Разработка

Node.js 22.

Исправления безопасности транзитивных зависимостей закреплены в `overrides`:
`undici` — не ниже 7.30.2, `happy-dom` — 21.0.4. Все пакеты Payload остаются
на одной версии; обновление отдельных пакетов Payload требует отдельной проверки совместимости.

```bash
cp .env.example .env
npm install
npm run dev
```

Админка — http://localhost:3000, первый администратор берётся из `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Бот и синхронизация заказов запускаются только с `RUN_BOT=1`. Не включайте его с токеном работающего бота: две копии будут отнимать друг у друга сообщения. Без токена `RUN_BOT=1` включает одну синхронизацию: укажите `ORDERS_DIR` и `PRICES_FILE` (например, `../src/prices.json`).

После изменения коллекций:

```bash
npm run generate:types
npm run migrate:create -- <название>
```

Миграции из `src/migrations/` применяются на хостинге при запуске.

## Деплой

Workflow **Admin** (`.github/workflows/admin.yml`) запускается при изменениях в `admin/`:

| Ветка        | Админка                          | Бот                             | Заказы сайта               |
| ------------ | -------------------------------- | ------------------------------- | -------------------------- |
| `main`       | `admin.brandmasterskaya.ru`      | @masterskaya_brand_strategy_bot | `brandmasterskaya.ru`      |
| любая другая | `admin.test.brandmasterskaya.ru` | @masterskaya_brand_test_bot     | `test.brandmasterskaya.ru` |

Ограничения хостинга reg.ru (Host-0), под которые всё устроено:

- процесс, который слушает TCP-порт, хостинг убивает за секунды — поэтому Node слушает unix-сокет (`deploy/listen-unix.cjs`);
- под Passenger запускаются только Python-приложения — поэтому `deploy/passenger_wsgi.py` запускает Node и проксирует ему запросы. Node-процесс живёт отдельно от Python и переживает его остановку;
- память — 1 ГБ на процесс, а сборке нужно около 3 ГБ — поэтому сборка идёт в GitHub Actions, на сервер едет готовый standalone-сервер (около 2 000 файлов);
- под Passenger виртуальная память ограничена 1,5 ГБ — Node запускается с `--disable-wasm-trap-handler`.
- на аккаунт не больше 36 потоков — драйвер SQLite и Node ограничены (`TOKIO_WORKER_THREADS=1`, `UV_THREADPOOL_SIZE=2`, `--v8-pool-size=2`), процесс держит около 8 потоков;
- соединения с `api.telegram.org` по IPv4 зависают на две минуты — бот ходит в Telegram через Cloudflare Worker из `worker/` (`TELEGRAM_API_URL`).

На сервере:

| Путь                             | Что                                                                  |
| -------------------------------- | -------------------------------------------------------------------- |
| `~/apps/node/`                   | Node.js 22 (системный слишком старый)                                |
| `~/apps/<админка>/app/`          | собранное приложение                                                 |
| `~/www/<админка>/`               | `passenger_wsgi.py` и `.htaccess` (`PassengerEnabled On`)            |
| `~/private/<админка>/env.json`   | секреты и пути, пишет деплой                                         |
| `~/private/<админка>/payload.db` | база                                                                 |
| `~/private/<админка>/app.log`    | лог приложения и бота                                                |
| crontab                          | раз в 5 минут открывает админку, чтобы поднять её после перезагрузки |

В панели reg.ru у сайта админки должны быть включены **PHP** и **Python**.

Секреты репозитория: `ADMIN_PAYLOAD_SECRET` (подпись сессий), `ADMIN_PASSWORD` (первый администратор `contact@brandmasterskaya.ru`), токены ботов `TG_BOT_MASTERSKAYA_TOKEN` и `TG_TESTBOT_MASTERSKAYA_TOKEN`, доступ к серверу — как у сайта.

## Персональные ссылки и рассылки

В карточках **Заказа** и **Участника** есть поле «Персональная ссылка на бота».
Имя бота задаётся через `TELEGRAM_BOT_USERNAME` либо определяется по `TELEGRAM_BOT_TOKEN`.
Для локальной админки без токена задайте `TELEGRAM_BOT_USERNAME=masterskaya_brand_test_bot`.
У нового заказа персональная ссылка появляется после первого сохранения. Ссылка заказа содержит `start=<номер заказа>`:
существующая проверка оплаты и привязки к Telegram-аккаунту остаётся обязательной.
У участника используется последний оплаченный заказ; без заказа — обычная ссылка на бота.

Раздел **Рассылки**:

1. Создайте черновик, выберите отправителя: бот или личный аккаунт `@brandmasterskaya`.
2. Выберите участников и/или заказы либо всех получателей по фильтру. Фильтры оплаты
   и тарифов применяются вместе к одному заказу. Повторные заказы одного Telegram-пользователя
   не создают повторных сообщений.
3. Напишите текст с переменными: `{name}`, `{first_name}`, `{username}`, `{email}`,
   `{phone}`, `{bot_link}`, `{order_id}`, `{site}`. Для ссылки на текст используйте
   `[Перейти в бота]({bot_link})` или `[Открыть сайт](https://example.com)`.
   В редакторе есть меню **Вставить переменную** и кнопки оформления выделенного текста:
   цитата, скрытый текст, жирный, курсив, подчёркивание, зачёркивание, моноширинный текст,
   дата и время, ссылка и очистка оформления. Изменения сразу видны в редакторе.
   В диалоге ссылки можно выбрать персональную ссылку на бота; дата вводится по Москве
   и передаётся в Telegram как дата, которую получатель видит в своём часовом поясе.
   Старые текстовые шаблоны продолжают открываться с сохранением переменных и ссылок.
   В Telegram отображается кликабельная подпись, адрес скрыт. Ссылки работают от бота
   и от личного аккаунта; в предпросмотре они тоже кликабельны. HTML не обрабатывается.
   Данные берутся из последнего подходящего заказа. Пустое значение заменяется пустой строкой.
4. Сохраните черновик, нажмите **Предпросмотр и получатели**, проверьте персональные тексты
   и пропущенных получателей. Затем нажмите **Отправить … получателям**.
5. Результаты видны в карточке рассылки. После запуска текст и получатели не меняются.

Бот пишет только участникам, которые уже обращались к нему. Заказам без Telegram-аккаунта
можно отправить приглашение из личного аккаунта: нужен username в поле Telegram либо телефон,
который доступен в контактах этого аккаунта. Telegram может запрещать конкретный диалог;
такие получатели отображаются в предпросмотре как пропущенные.

### Подключение @brandmasterskaya

Откройте **Настройки → Telegram @brandmasterskaya**. Получите `api_id` и `api_hash`
собственного приложения на [my.telegram.org/apps](https://my.telegram.org/apps), введите их
и телефон аккаунта, запросите код. Введите код из Telegram и пароль двухэтапной
аутентификации, если он включён. Подключить другой аккаунт нельзя.
Код и пароль вводятся только в админке, передавать их разработчику не нужно.
Кнопка отключения отзывает созданную сессию Telegram.

Используется MTProto (`teleproto`), без окна Telegram Business в 24 часа. Ограничения
личного аккаунта Telegram сохраняются. Между отправками из аккаунта — минимум 3 секунды;
`FLOOD_WAIT` и HTTP 429 сохраняют время продолжения в БД. Обработчик продолжает после паузы.

Ключи приложения и сессия зашифрованы AES-256-GCM с ключом от `PAYLOAD_SECRET`
(минимум 32 символа). Поле сессии скрыто и закрыто для чтения через API даже администраторам.
Смена `PAYLOAD_SECRET` требует повторного подключения аккаунта. Код входа действует
10 минут и привязан к администратору, который его запросил.

Очередь обрабатывается в существующем единственном Node-процессе с `RUN_BOT=1`.
MTProto требует исходящего соединения с дата-центрами Telegram; HTTP-посредник бота
`TELEGRAM_API_URL` для MTProto не используется. Доступность этих соединений нужно проверить
на хостинге при подключении аккаунта.

Перед сетевой отправкой обработчик сохраняет состояние `sending`. После перезапуска
незавершённая отправка получает `uncertain` и автоматически не повторяется: Telegram мог уже
принять сообщение. Проверьте диалог перед ручным повтором. Остальная очередь продолжается.

Проверки: `npm test`, `npm run typecheck`, `npm run build` в `admin/`. Тесты не отправляют
реальные сообщения и применяют production-миграции к отдельной временной SQLite-базе.

### Редактор автоматических ответов

В «Текстах бота» используется тот же редактор с кнопками оформления, что и в рассылках.
Меню предлагает `{name}`, `{site}`, `{contact}`; в сообщении «Оплата подтверждена»
дополнительно доступны `{items}` и `{total}`. Старые тексты и ссылки сохраняют совместимость.
Ошибки в новых форматированных шаблонах проверяются при сохранении.

### Добавление заказов списком

В списке заказов откройте «Добавить заказы списком». Можно вставить таблицу из Excel /
Google Sheets или открыть CSV / TSV. Шаблон заголовков скачивается там же:
`Имя`, `Email`, `Телефон`, `Telegram`, `Тарифы`, `Сумма`, `Оплачен`.
Обязательно только имя; лишние колонки и повторные заголовки не принимаются.

Сначала проверьте предпросмотр, затем добавьте заказы. Один импорт — до 1000 строк и 1 МБ.
В тарифах указываются ключи или точные названия через `|`; пустая ячейка использует
тарифы по умолчанию из формы. Пустая сумма считается по ценам выбранных тарифов.
Пустая дата означает неоплаченный заказ. Принимаются даты `ДД.ММ.ГГГГ` и ISO;
даты без часового пояса интерпретируются по Москве.

Импорт выполняется в отдельной транзакции: при ошибке записи вся пачка отменяется.
Повтор запроса с тем же идентификатором пачки не дублирует уже добавленные строки.
После успешного импорта кнопка «Новый импорт» начинает новую независимую пачку.
Добавленные заказы считаются ручными: сумму, дату оплаты и позиции можно менять позже.

### Выбор получателей в таблице

В рассылке выберите оплату и тарифы, затем отметьте участников и/или заказы в таблицах.
Доступны поиск по имени и контактам, просмотр только выбранных и выбор всей страницы.
Кнопки «Выбрать всех по фильтру» и «Снять выбор по фильтру» действуют на все страницы,
сохраняя остальные отмеченные строки. Фильтры оплаты и тарифа должны совпасть в одном заказе.

Поле «Автоматически продолжится после» появляется только во время паузы, назначенной
Telegram из-за ограничения отправки. Время задаёт обработчик; вручную его менять не нужно.

### Запланированные и повторяющиеся рассылки

В карточке рассылки выберите **Когда отправлять**: сейчас, один раз по дате,
ежедневно, еженедельно или ежемесячно. **Первый запуск** задаёт время и день повторов.
Все поля расписания вводятся и показываются по Москве (UTC+3), независимо от часового пояса браузера.
Для повторов можно указать **Повторять до** включительно; пустое поле означает повторы до остановки.
Еженедельная рассылка повторяет день недели первого запуска. Ежемесячная сохраняет исходный
день месяца: для 31-го числа в феврале используется последний день, в марте снова 31-е.

Сохранение создаёт только черновик. Откройте предпросмотр и нажмите **Включить расписание**.
Начальная дата при подтверждении должна быть в будущем. Предпросмотр показывает текущую аудиторию;
перед каждым запуском получатели и переменные вычисляются заново по сохранённым условиям.
Можно включить расписание с пустой текущей аудиторией: к первому запуску участники могут появиться.
Для неизменного списка используйте выбранных участников/заказы; фильтры всё равно проверяются при запуске.
Правила одинаковы для бота и личного аккаунта. После включения настройки фиксируются.

**Остановить расписание** отменяет будущие запуски. Уже созданная отправка завершается.
В карточке видны следующий запуск и **История запусков**; каждый запуск имеет отдельную карточку
с результатами доставки и ссылкой на исходное расписание. При ошибке подготовки расписание
останавливается, причина видна в карточке. Запуск без доступных получателей завершается без отправки.

Расписания проверяет существующий обработчик каждые 5 секунд при `RUN_BOT=1`.
Выключенный сервер или занятый обработчик могут задержать отправку. После восстановления создаётся
один пропущенный запуск, затем ближайший будущий срок; накопленные повторы не отправляются пачкой.
Запуски одного расписания не пересекаются. Уникальный ключ срабатывания предотвращает дублирование
карточки после перезапуска; существующая защита от повторной неопределённой доставки сохраняется.

Миграция `20261107_063906_broadcast_schedules` добавляет поля и индексы без изменения прежних рассылок.
При откате расписания переводятся в завершённые; карточки запусков, результаты доставки и прежние связи
с участниками и заказами сохраняются. Даты и связи с исходным расписанием при откате удаляются.
Перед деплоем используется штатная резервная копия базы из workflow Admin.

## Личный кабинет и записи лекций

Кабинет работает на домене лендинга: `https://brandmasterskaya.ru/cabinet/`,
тестовый — `https://test.brandmasterskaya.ru/cabinet/`. Новые DNS-записи и сертификаты не нужны.
PHP-шлюз `src/cabinet/index.php` передаёт только запросы кабинета в Unix-сокет
существующей админки. Лендинг и PHP API оплаты продолжают обслуживаться напрямую.
Вторые Node-процесс, бот и база не запускаются.

JavaScript и CSS Next.js доступны по `/cabinet/_next/static/`; шлюз отображает этот путь
на `/_next/static/` внутри Node. На домене админки такой же путь обслуживает rewrite Next.js.
`skipTrailingSlashRedirect` предотвращает цикл между Apache DirectorySlash и Next.js.

В Payload откройте **Личный кабинет → Лекции**. Загрузите MP4 с аудиодорожкой,
выберите **Доступ по тарифам и факультативам** и отметьте «Опубликована».
Лекция доступна после успешной подготовки при наличии оплаченного заказа с любым
выбранным продуктом. Заказ должен быть привязан к аккаунту Telegram и находиться вне корзины.
Без выбранных тарифов и факультативов доступа нет. Учебные группы убраны из админки,
API и проверки доступа; старые таблицы сохранены только для отката миграции.
Отмена оплаты, перенос заказа в корзину или смена привязки отзывают доступ при следующем запросе видео.
Пользователь появляется в «Участниках» после первого входа через Telegram или обращения к боту.

Интерфейс использует цвета лендинга: бумага `#efeee7`, текст `#22231f`, красный `#dc3e27`,
линии `#cfcec6`, вторичный текст `#64655e`; Helvetica и крупные заголовки.
Каталог показывает только доступные лекции, поддерживает поиск и просмотр записи.

### Настройка окружения

- `CABINET_URL` — HTTPS origin лендинга без пути; локально `http://localhost:3000`.
- `CABINET_SECRET` — отдельный случайный секрет длиной не менее 32 символов.
  Используется для сессий, временных разрешений и получения ключей видео.
- `TELEGRAM_LOGIN_CLIENT_ID`, `TELEGRAM_LOGIN_CLIENT_SECRET` — реквизиты OIDC
  из BotFather → нужный бот → Login Widget. Оставьте алгоритм подписи RS256.
  Разрешите точный адрес `https://brandmasterskaya.ru/cabinet/auth/callback`; для тестового бота —
  `https://test.brandmasterskaya.ru/cabinet/auth/callback`.
- `LECTURE_STORAGE_DIR` — абсолютный путь вне `www/` и каталога приложения,
  например `~/private/<админка>/lectures` (в переменной нужен раскрытый абсолютный путь).
- `RUN_LECTURE_WORKER=1` — включить последовательную подготовку видео в приложении.
  Тестовый деплой устанавливает и проверяет приватные FFmpeg 7.0.2 и Shaka Packager 3.9.3
  на синтетическом видео, затем включает очередь. `TEST_RUN_LECTURE_WORKER=0` выключает её.
  На production включение остаётся отдельной настройкой после проверки инфраструктуры.
- `FFMPEG_PATH`, `SHAKA_PACKAGER_PATH` — абсолютные пути к FFmpeg и Shaka Packager;
  без переменных используются `ffmpeg` и `packager` из PATH.

Вход использует Telegram OIDC Authorization Code Flow с PKCE и проверкой state,
подписи, issuer, audience и срока токена. Telegram `id` привязывается к участнику;
OIDC `sub` не используется вместо Bot API ID. Сессия кабинета действует 24 часа,
не даёт доступа к Payload и хранится в host-only HttpOnly cookie.

После настройки `CABINET_URL` бот показывает кнопку «Перейти в личный кабинет»
по `/start`. Бот не выдаёт доступ к лекциям по самому факту входа.

### Подготовка и хранение видео

Загрузка ограничена 128 МиБ. На прокси админки тело загрузки ещё проходит
через память Python, поэтому повышать лимит без проверки памяти нельзя.
Для более длинных лекций уменьшите размер MP4 или разделите запись на части.
FFmpeg перекодирует видео максимум до ширины 1280 пикселей, H.264/AAC;
Shaka Packager создаёт зашифрованные DASH и HLS с сегментами по шесть секунд.
DASH явно использует `--generate_static_live_mpd`, HLS — `--hls_playlist_type VOD`: запись
имеет конечную длительность и открывается с начала. Тестовый деплой исправляет старые
завершённые dynamic MPD без изменения шифрования и сегментов; оригинал остаётся
в приватном файле `manifest.mpd.pre-vod`, который не выдаётся медиамаршрутом.
В редакторе лекции прогресс обновляется каждые две секунды без потери несохранённых правок.
Первые 90% рассчитываются по времени закодированного видео, оставшиеся 10% отведены
шифрованию и публикации. 100% появляется только после успешной публикации.
Плеер кабинета использует DASH и Clear Key; это не Widevine или FairPlay.
Safari и встроенные браузеры Telegram требуют отдельной проверки совместимости;
при отсутствии поддержки предложено открыть актуальный Chrome или Firefox.

Исходники лежат в `sources/`, зашифрованные фрагменты — в `streams/<версия>/`,
промежуточные файлы — в `work/`. Доступ к исходникам через Payload закрыт всем,
кроме администраторов. Нельзя публиковать эти каталоги как статические файлы.
Ключи не записываются в БД, плейлисты или подписанные разрешения.
Shaka Packager получает ключ в аргументах процесса: пользователь ОС с доступом
к процессам этого аккаунта может его увидеть. Это не аппаратная защита ключа.

Подготовка выполняется по одному заданию. Переименование готового каталога атомарно;
замена исходника меняет версию и не позволяет опубликовать результат старого задания.
Ошибка видна в админке. Для повторной подготовки загрузите MP4 заново.
Если процесс остановлен во время обработки, задача возвращается в очередь после двух минут
без heartbeat. Старый обработчик не может изменить статус новой попытки благодаря
отдельному токену задания. Повторная загрузка создаёт новое задание. Старые версии фрагментов сохраняются на диске:
перед ручной очисткой сверьте версии с текущими лекциями и сделайте резервную копию.

Разрешение просмотра действует десять минут и обновляется плеером каждые четыре минуты.
Каждый запрос фрагмента и ключа повторно проверяет сессию, версию видео,
публикацию и оплаченные покупки. Отзыв доступа запрещает новые запросы; уже буферизованные
секунды видео могут продолжить воспроизведение. Копии, ранее сохранённые зрителем,
отозвать невозможно. Смена `CABINET_SECRET` завершает сессии и требует заново обработать
все видео: ключи текущих фрагментов перестанут совпадать с выдаваемыми.

Просмотр использует интерфейс Shaka Player: перемотку, громкость, скорость и полноэкранный режим.
Видимая метка пользователя отсутствует; невидимая метка и forensic watermarking пока не внедрены.
Clear Key не предотвращает извлечение ключа авторизованным зрителем и не блокирует запись экрана.

### Размещение на домене лендинга

Существующих PHP с cURL и Apache mod_rewrite на сайте достаточно; Python/Passenger
по-прежнему нужны только админке. Поддержку `CURLOPT_UNIX_SOCKET_PATH` на хостинге
нужно проверить перед первым запуском. Корневой `.htaccess` сайта не меняется:
правила маршрутизации ограничены каталогом `cabinet/`.

В GitHub настройте отдельно:

| Production                            | Test                                       |
| ------------------------------------- | ------------------------------------------ |
| secret `CABINET_SECRET`               | secret `TEST_CABINET_SECRET`               |
| variable `TELEGRAM_LOGIN_CLIENT_ID`   | variable `TEST_TELEGRAM_LOGIN_CLIENT_ID`   |
| secret `TELEGRAM_LOGIN_CLIENT_SECRET` | secret `TEST_TELEGRAM_LOGIN_CLIENT_SECRET` |
| variable `RUN_LECTURE_WORKER`         | variable `TEST_RUN_LECTURE_WORKER`         |

`CABINET_URL` в workflow вычисляется из `SITE`: production всегда использует
`https://brandmasterskaya.ru`, test — `https://test.brandmasterskaya.ru`.
Прежние GitHub variables `CABINET_URL` и `TEST_CABINET_URL` больше не используются.
Пути к установленным бинарным файлам задаются variables `FFMPEG_PATH` и `SHAKA_PACKAGER_PATH`.

Workflow Admin копирует публичный шлюз в `~/www/<сайт>/cabinet/` и записывает
его конфигурацию в `~/private/<сайт>/cabinet-proxy.php`: путь к Unix-сокету своей админки
и фиксированные HTTPS origins. Workflow Deploy включает шлюз в сборку лендинга;
исключение `.htaccess` в rsync относится только к корню сайта, поэтому правила
`cabinet/.htaccess` обновляются. Платёжный `config.php` и корневые правила не меняются.

Шлюз передаёт cookies и временный токен, поддерживает потоковую выдачу фрагментов,
не передаёт произвольные Authorization/Host и не даёт обращаться к `/admin` или `/api`.
POST ограничен 4096 байтами: загружать лекции нужно через домен админки.
Если сокет недоступен, шлюз один раз обращается к `/api/users/me` админки,
чтобы Passenger запустил существующий процесс, и повторяет только неподключённый запрос.
Сессионные данные зрителя на этот служебный запрос не передаются.

На хостинге ещё нужно проверить шлюз, вход и ресурсы кабинета; локальные проверки
не подтверждают настройки Apache/reg.ru. Созданные ранее поддомены кабинета не используются.

Миграция `20261108_033144_lecture_cabinet` добавляет только новые таблицы и связи блокировок.
Штатный workflow делает резервную копию SQLite перед обновлением. Отмена миграции удаляет
метаданные кабинета и назначения групп, но сохраняет прежние заказы, участников и файлы видео.
Для возврата данных кабинета восстановите соответствующую резервную копию БД и приватного хранилища.

### Проверки кабинета

`npm test` проверяет токены, Telegram JWT на синтетических ключах, кнопку бота,
приватность коллекций, отзыв доступа по покупкам, замену видео во время обработки и откат миграции
с сохранением прежних заказов и участников. `cabinetProxy.test.mjs` проверяет маршруты шлюза и заголовки, включая закодированные переходы к маршрутам админки.

Для покрытия серверной логики:

```bash
node --import tsx --experimental-test-coverage --test-coverage-include='src/cabinet/*.ts' --test tests/cabinet*.test.mjs
```

При разработке воспроизведены падающие проверки отсутствующей реализации,
публикации устаревшего задания (`ready` вместо `pending`) и обхода маршрутов прокси.
После исправлений все эти проверки проходят. Покрытие загруженных серверных модулей —
93,84% строк; React-компоненты и Next.js route handlers в эту цифру не входят.
Отдельно проверены реальные FFmpeg/Shaka Packager и HTTP-выдача тестовых DASH/HLS,
ключей, отказ без сессии и токена, CSRF и выход из кабинета на временной базе.
PHP-шлюз дополнительно проверен с настоящим Unix-сокетом Node: оба варианта `/cabinet`
и `/cabinet/`, префиксованные JS/CSS, фрагменты видео, ключи, cookies выхода и лимит POST.
Реальный Telegram-вход и воспроизведение через браузерный CDM ещё требуют проверки
после настройки окружения. Визуальная проверка через подключённый браузер не завершилась:
расширение не ответило при открытии локальной страницы.
